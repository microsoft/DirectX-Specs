# Indirect execution

A command signature describes a fixed-format record of arguments and state changes followed by one work command. `ExecuteIndirect` interprets an array of these records on the GPU. Recording the call does not capture the argument-buffer or count-buffer contents.

The command signature selects the record format, not a pipeline, shaders, render targets or descriptor heaps. State not supplied by the signature is inherited from the command list. The selected work command retains the direct operation's pipeline, resource, dimension and execution-context requirements.

For example, suppose an application wants a unique root constant to be
specified per-draw call in the indirect argument buffer. The application
would create a command signature that enables the indirect argument
buffer to specify the following parameters per draw call:

- Draw arguments (Vertex Count, Instance Count, ...)

- The value of 1 root constant

The indirect argument buffer generated by the application would contain
an array of fixed-size records. Each structure corresponds to 1 draw
call. Each structure contains the drawing arguments, and the value of
the root constant. The number of draw calls can be specified in a separate
GPU-visible buffer or by `MaxCommandCount`.

An example command buffer generated by the application would look like:

|**Command Buffer Format**| |
|-|-|
|`RootConstant (RootParameterIndex=1)`|   Draw structure \#1|
|`VertexCount`||
|`InstanceCount`||
|`StartVertexLocation`||
|`StartInstanceLocation`||
|`RootConstant (RootParameterIndex=1)`|   Draw structure \#2|
|`VertexCount`||
|`InstanceCount`||
|`StartVertexLocation`||
|`StartInstanceLocation`||
|`RootConstant (RootParameterIndex=1)`|   Draw structure \#3|
|`VertexCount`||
|`InstanceCount`||
|`StartVertexLocation`||
|`StartInstanceLocation`||

<a id="command-signatures"></a>

## Command signatures and argument descriptions

`ID3D12CommandSignature` derives from `ID3D12Pageable`, which derives from `ID3D12DeviceChild` and `ID3D12Object`, then `IUnknown`. It declares no additional methods. The standard inherited object, device-child and pageable responsibilities are unchanged; inherited methods are not separate command-signature APIs.

The command signature retains its root-signature object. The application must keep the command signature, argument/count resources, and resources addressed by argument GPU virtual addresses alive and resident for their GPU use, following [execution lifetime](execution.md#lifetime) and [residency](resources.md#residency). Command recording does not take ownership of application storage or freeze its contents.

<a id="command-signature-desc"></a>

### D3D12_COMMAND_SIGNATURE_DESC

```cpp
typedef struct D3D12_COMMAND_SIGNATURE_DESC
{
    // The number of bytes between each drawing structure
    UINT ByteStride;
    UINT NumArgumentDescs;
    const D3D12_INDIRECT_ARGUMENT_DESC* pArgumentDescs;
    UINT NodeMask;
} D3D12_COMMAND_SIGNATURE_DESC;
```

#### Members

`ByteStride`

Specifies the size of each command in the drawing buffer, in bytes.

`NumArgumentDescs`

Specifies the number of arguments in the command signature.

`pArgumentDescs`

An array of [D3D12_INDIRECT_ARGUMENT_DESC](#indirect-argument-desc) structures, containing details of the arguments, including whether the argument is a vertex buffer, constant, constant buffer view, shader resource view, or unordered access view.

`NodeMask`

For single GPU operation, set this to zero. If there are multiple GPU nodes, set bits to identify the nodes (the device's physical adapters) for which the command signature is to apply. Each bit in the mask corresponds to a single node. Refer to [Multi-adapter systems](https://learn.microsoft.com/en-us/windows/win32/direct3d12/multi-engine).

### D3D12_INDIRECT_ARGUMENT_DESC

```cpp
typedef struct D3D12_INDIRECT_ARGUMENT_DESC
{
    D3D12_INDIRECT_ARGUMENT_TYPE Type;

    union
    {
        struct
        {
            UINT Slot;
        } VertexBuffer;

        struct
        {
            UINT RootParameterIndex;
            UINT DestOffsetIn32BitValues;
            UINT Num32BitValuesToSet;
        } Constant;

        struct
        {
            UINT RootParameterIndex;
        } ConstantBufferView;

        struct
        {
            UINT RootParameterIndex;
        } ShaderResourceView;

        struct
        {
            UINT RootParameterIndex;
        } UnorderedAccessView;

        // Tier 1.1 support
        struct
        {
            UINT RootParameterIndex;
            UINT DestOffsetIn32BitValues;
        } IncrementingConstant;
    };
} D3D12_INDIRECT_ARGUMENT_DESC;
```

#### Members

`Type`

A single [D3D12_INDIRECT_ARGUMENT_TYPE](#indirect-argument-type) enumeration constant.

`VertexBuffer.Slot`

Specifies the slot containing the vertex buffer address.

`Constant.RootParameterIndex`

Specifies the root index of the constant.

`Constant.DestOffsetIn32BitValues`

The offset, in 32-bit values, to set the first constant of the group. Supports multi-value constants at a given root index. Root constant entries must be sorted from smallest to largest DestOffsetIn32BitValues.

`Constant.Num32BitValuesToSet`

The number of 32-bit constants that are set at the given root index. Supports multi-value constants at a given root index.

`ConstantBufferView.RootParameterIndex`

Specifies the root index of the CBV.

`ShaderResourceView.RootParameterIndex`

Specifies the root index of the SRV.

`UnorderedAccessView.RootParameterIndex`

Specifies the root index of the UAV.

`IncrementingConstant.RootParameterIndex`

Specifies the root-constant parameter index.

`IncrementingConstant.DestOffsetIn32BitValues`

Specifies the single 32-bit constant to update within that parameter.

<a id="argument-records"></a>

## Argument records and packing

The ordering of arguments within an indirect argument buffer is defined
to exactly match the order of arguments specified in
`D3D12_COMMAND_SIGNATURE_DESC::pArgumentDescs`. All of the arguments for 1
draw/dispatch call within an indirect argument buffer are tightly
packed. However, applications are allowed to specify an arbitrary byte
stride between draw/dispatch commands in an indirect argument buffer.

`D3D12_INDIRECT_ARGUMENT_TYPE_INCREMENTING_CONSTANT` is a unique argument type in that it doesn't occupy any argument buffer space. See [Incrementing constant](#incrementing-constant).

```cpp
typedef struct D3D12_DRAW_ARGUMENTS
{
    UINT VertexCountPerInstance;
    UINT InstanceCount;
    UINT StartVertexLocation;
    UINT StartInstanceLocation;
} D3D12_DRAW_ARGUMENTS;
```

```cpp
typedef struct D3D12_DRAW_INDEXED_ARGUMENTS
{
    UINT IndexCountPerInstance;
    UINT InstanceCount;
    UINT StartIndexLocation;
    INT  BaseVertexLocation;
    UINT StartInstanceLocation;
} D3D12_DRAW_INDEXED_ARGUMENTS;
```

```cpp
typedef struct D3D12_DISPATCH_ARGUMENTS
{
    UINT ThreadGroupCountX;
    UINT ThreadGroupCountY;
    UINT ThreadGroupCountZ;
} D3D12_DISPATCH_ARGUMENTS;
```

```cpp
typedef struct D3D12_DISPATCH_MESH_ARGUMENTS

    UINT ThreadGroupCountX;

    UINT ThreadGroupCountZ;
} D3D12_DISPATCH_MESH_ARGUMENTS;
```

```cpp
typedef struct D3D12_VERTEX_BUFFER_VIEW
{
    D3D12_GPU_VIRTUAL_ADDRESS BufferLocation;
    UINT SizeInBytes;
    UINT StrideInBytes;
} D3D12_VERTEX_BUFFER_VIEW;
```

```cpp
typedef struct D3D12_INDEX_BUFFER_VIEW
{
    D3D12_GPU_VIRTUAL_ADDRESS BufferLocation;
    UINT SizeInBytes;
    DXGI_FORMAT Format;
} D3D12_INDEX_BUFFER_VIEW;
```

The complete [D3D12_DISPATCH_RAYS_DESC](raytracing-pipelines.md#d3d12_dispatch_rays_desc), [D3D12_GPU_VIRTUAL_ADDRESS_RANGE](raytracing-pipelines.md#d3d12_gpu_virtual_address_range) and [D3D12_GPU_VIRTUAL_ADDRESS_RANGE_AND_STRIDE](raytracing-pipelines.md#d3d12_gpu_virtual_address_range_and_stride) declarations and field contracts are defined with ray dispatch. The exact indirect payload sizes, offsets and concatenation rules below remain defined here.

The enum/union above describes the signature on the CPU; it is not copied into each argument record. Only the selected payload is stored. These are byte sizes, not host-language alignments to insert between arguments.

| Argument type (prefix `D3D12_INDIRECT_ARGUMENT_TYPE_`) | Payload in one record | Bytes |
|---|---|---:|
| `DRAW` | `D3D12_DRAW_ARGUMENTS` | 16 |
| `DRAW_INDEXED` | `D3D12_DRAW_INDEXED_ARGUMENTS` | 20 |
| `DISPATCH` | `D3D12_DISPATCH_ARGUMENTS` | 12 |
| `VERTEX_BUFFER_VIEW` | `BufferLocation` (64 bits), `SizeInBytes`, `StrideInBytes` | 16 |
| `INDEX_BUFFER_VIEW` | `BufferLocation` (64 bits), `SizeInBytes`, `Format` | 16 |
| `CONSTANT` | `Constant.Num32BitValuesToSet` consecutive 32-bit values | `4 * Num32BitValuesToSet` |
| `CONSTANT_BUFFER_VIEW`, `SHADER_RESOURCE_VIEW`, `UNORDERED_ACCESS_VIEW` | One `D3D12_GPU_VIRTUAL_ADDRESS` | 8 each |
| `DISPATCH_RAYS` | `D3D12_DISPATCH_RAYS_DESC`, including its trailing structure padding | 104 |
| `DISPATCH_MESH` | `D3D12_DISPATCH_MESH_ARGUMENTS` | 12 |
| `INCREMENTING_CONSTANT` | No argument-buffer payload | 0 |

Argument offsets are the prefix sum of these payload sizes in descriptor order. There is no implicit alignment gap between arguments, including before an eight-byte GPU virtual address. `ByteStride` must be four-byte aligned and at least the sum of the payload sizes. Additional bytes may occur after the argument payload and before the next record.

Within `D3D12_DISPATCH_RAYS_DESC`, `RayGenerationShaderRecord` occupies bytes 0–15; `MissShaderTable`, `HitGroupTable` and `CallableShaderTable` occupy 16–39, 40–63 and 64–87. `Width`, `Height` and `Depth` occupy 88–91, 92–95 and 96–99; bytes 100–103 are trailing structure padding. The ranges store `StartAddress`, then `SizeInBytes`, and, where present, `StrideInBytes`, each as 64-bit values. Tightly packed argument concatenation does not remove padding *inside* the public payload structure. A host C++ aggregate can also introduce padding *between* its members; such padding must not be mistaken for the signature-defined layout. Serialize to the prescribed offsets or make the host layout match them.

<a id="draw-arguments"></a>

### Non-indexed draw fields

`DRAW` consumes the following `D3D12_DRAW_ARGUMENTS` fields, in order:

| Field | Meaning |
|---|---|
| `UINT VertexCountPerInstance` | How many vertices to read sequentially from Buffer(s) marked as Vertex Data (same set repeated for each Instance). |
| `UINT InstanceCount` | How many Instances to render. |
| `UINT StartVertexLocation` | Which Vertex to start at in each Buffer marked as Vertex Data (for each Instance). |
| `UINT StartInstanceLocation` | Which Instance to start sequentially fetching from in each Buffer marked as Instance Data. |

The argument resource is a buffer containing full command-signature records. The draw payload above begins at its signature-defined offset within each record, after any preceding constant or view payloads. `ArgumentBufferOffset` selects the first full record at a DWORD-aligned byte offset; `ByteStride` separates successive full records. [Argument initialization](#argument-initialization) describes ways to initialize them.

If the address range in the buffer where the draw parameters will be fetched from would go out of bounds of the buffer, behavior is undefined. D3D12's [recording-time extent validation](#execute-validation) checks the range selected by `MaxCommandCount`; a smaller GPU count is not a substitute for that validation.

<a id="draw-indexed-arguments"></a>

### Indexed draw fields

`DRAW_INDEXED` consumes the following `D3D12_DRAW_INDEXED_ARGUMENTS` fields, in order:

| Field | Meaning |
|---|---|
| `UINT IndexCountPerInstance` | How many indices to read sequentially from the Index Buffer (same set repeated for each Instance). |
| `UINT InstanceCount` | How many Instances to render. |
| `UINT StartIndexLocation` | Which Index to start at in the Index Buffer (for each Instance). |
| `INT BaseVertexLocation` | Which Vertex in each buffer marked as Vertex Data to consider as Index "0". Note that this value is signed. A negative BaseVertexLocation allows, for example, the first vertex to be referenced by an index value > 0. |
| `UINT StartInstanceLocation` | Which Instance to start sequentially fetching from in each Buffer marked as Instance Data. |

The argument resource is a buffer containing full command-signature records. The indexed-draw payload above begins at its signature-defined offset within each record, after any preceding constant or view payloads. `ArgumentBufferOffset` selects the first full record at a DWORD-aligned byte offset; `ByteStride` separates successive full records. [Argument initialization](#argument-initialization) describes ways to initialize them.

If the address range in the buffer where the indexed-draw parameters will be fetched from would go out of bounds of the buffer, behavior is undefined. D3D12's [recording-time extent validation](#execute-validation) applies independently of the eventual GPU count.

Each draw record has the semantics of [DrawInstanced](vertex-processing.md#drawinstanced) or [DrawIndexedInstanced](vertex-processing.md#drawindexedinstanced) with these field values. A zero per-instance count or zero `InstanceCount` generates no primitives, but is still a record in the indirect command sequence. The [address-generation algorithms](vertex-processing.md#address-generation), [indexed arithmetic](vertex-processing.md#indexed-addresses), [generated vertex/primitive/instance IDs](vertex-processing.md#generated-identifiers), [input fetching and bounds](vertex-processing.md#fetching-rules), [32-bit arithmetic](vertex-processing.md#arithmetic), [alignment](vertex-processing.md#alignment), [format conversion](vertex-processing.md#conversion) and [input packing example](vertex-processing.md#worked-example) apply unchanged. Argument-buffer fetch bounds are distinct from vertex/index-data fetch bounds.

<a id="dispatch-arguments"></a>

### Dispatch fields and deferred reads

`DISPATCH` takes the information about how many thread groups to dispatch from a buffer on the GPU. When the command reaches the GPU for execution, at that time the parameters are read from the GPU buffer. The point is that the parameters may have been written by some other GPU operation, possibly after the actual issuing of the `ExecuteIndirect` call from the CPU.

At the specified record offset, the three `UINT` data members `ThreadGroupCountX`, `ThreadGroupCountY` and `ThreadGroupCountZ` of [D3D12_DISPATCH_ARGUMENTS](#argument-records) will be read.

If any of the dispatch arguments are 0, the dispatch does nothing. The [shared dispatch-dimension contract](compute.md#shared-grid-limits) defines the ordinary 65,535 per-axis limit and the capability-dependent expanded one-dimensional case, including its Y=Z=1 condition. Values larger than the applicable dimension bound produce undefined behavior. The [compute dispatch API](compute.md#dispatch) defines the workload and its pipeline/root-state prerequisites.

If the address range in the buffer where dispatch parameters will be fetched from goes out of bounds of the buffer, or the starting offset is not 4-byte aligned, behavior is undefined. D3D12 additionally performs the [recording-time validation](#execute-validation).

<a id="work-types"></a>

## Work types, capabilities and selected state

Exactly one work argument is required, and it must be the last argument description. It is one of `DRAW`, `DRAW_INDEXED`, `DISPATCH`, `DISPATCH_RAYS` or `DISPATCH_MESH`. The remaining argument descriptions update state for that work; they do not add more work commands to a record.

| Final work argument | Root-argument bind point | Workload and capability owner |
|---|---|---|
| `DRAW` / `DRAW_INDEXED` | Graphics | [Direct draws and IA/VS state](vertex-processing.md#direct-draws); [graphics pipelines](pipeline-state.md#graphics-description) |
| `DISPATCH` | Compute | [Compute stage](compute.md#stage-model), [Dispatch](compute.md#dispatch), [grid dimensions](compute.md#shared-grid-limits) |
| `DISPATCH_MESH` | Graphics | [MeshShaderTier and shader requirements](amplification-and-mesh-shaders.md#availability), [DispatchMesh](amplification-and-mesh-shaders.md#dispatchmesh), [AS payload/child-grid contract](amplification-and-mesh-shaders.md#payload-and-amplification), [shared grid limits](compute.md#shared-grid-limits) |
| `DISPATCH_RAYS` | Compute | [Raytracing tier 1.1](../Raytracing.md#d3d12_raytracing_tier), [DispatchRays](raytracing-pipelines.md#id3d12graphicscommandlist4dispatchrays), [descriptor and shader-table limits](raytracing-pipelines.md#d3d12_dispatch_rays_desc) |

`DISPATCH_MESH` consumes the standalone three-`UINT` payload, not a new argument-description union member. `ByteStride` includes the other selected arguments and any record-end padding; it is not required to equal 12 merely because the final work argument is a mesh dispatch.

The [full mesh/compute grid rules](compute.md#shared-grid-limits) apply to each record separately. Mesh grids retain their total-group bound `X*Y*Z < 2^22`; expanded X does not increase Y or Z. An AS-launched child grid is distinct from the indirect parent grid. Each ray record retains shader-table alignment/stride/extent and `Width*Height*Depth` limits from its exact descriptor owner. `MaxCommandCount` counts records, not vertices, instances, compute groups, AS-child groups or rays.

When a command signature configured for `DispatchRays` is passed to `ExecuteIndirect`, a raytracing pipeline state must be currently set on the command list otherwise behavior is undefined.

It is invalid for an application to modify the contents of [shader tables](raytracing-pipelines.md#shader-tables) from an ExecuteIndirect() call if that ExecuteIndirect() call references the same shader tables (e.g. via DispatchRays()).

### ExecuteIndirect tiers and incrementing constant

```cpp
typedef enum D3D12_EXECUTE_INDIRECT_TIER
{
    D3D12_EXECUTE_INDIRECT_TIER_1_0 = 10,
    D3D12_EXECUTE_INDIRECT_TIER_1_1 = 11,
} D3D12_EXECUTE_INDIRECT_TIER;
```

```cpp
typedef struct D3D12_FEATURE_DATA_D3D12_OPTIONS21
{
    D3D12_WORK_GRAPHS_TIER WorkGraphsTier;
    D3D12_EXECUTE_INDIRECT_TIER ExecuteIndirectTier;
    BOOL SampleCmpGradientAndBiasSupported;
    BOOL ExtendedCommandInfoSupported;
} D3D12_FEATURE_DATA_D3D12_OPTIONS21;
```

All D3D12 devices support tier 1.0.

Tier 1.1 adds support for [Incrementing constant](#incrementing-constant). Device support for tier 1.1 is reported in `D3D12_FEATURE_DATA_D3D12_OPTIONS21::ExecuteIndirectTier`, queried with `D3D12_FEATURE_D3D12_OPTIONS21` via `CheckFeatureSupport()`.

The incrementing constant is a unique argument type in that it doesn't occupy any argument buffer space.

Instead, `D3D12_INDIRECT_ARGUMENT_TYPE_INCREMENTING_CONSTANT` makes the system update a specified root constant for each executed command.  The configuration of the update is in the `IncrementingConstant` union entry of `D3D12_INDIRECT_ARGUMENT_DESC` (see [argument descriptions](#command-signatures)):

```cpp
struct
{
    UINT RootParameterIndex; // Must match with a root constant in the command signature's root signature
    UINT DestOffsetIn32BitValues; // Which constant in case the root constant has multiple
} IncrementingConstant;
```

From the shader point of view, accessing this is simply a matter of accessing the corresponding root constant.

The counter is a 32-bit UINT. For a given `ExecuteIndirect` call, the value starts at `0` for the first command and increments by `1` for each subsequent command.

A command signature can contain at most one incrementing constant.

`RootParameterIndex` must name a root-constant parameter, and `DestOffsetIn32BitValues` selects one value within it. The zero-byte payload still counts as an argument description, including for the bundle restriction. Its post-call value follows the canonical [indirect-state reset contract](command-list-state.md#indirect).

<a id="createcommandsignature"></a>

## ID3D12Device::CreateCommandSignature

### Declaration

```cpp
HRESULT CreateCommandSignature(
    const D3D12_COMMAND_SIGNATURE_DESC* pDesc,
    ID3D12RootSignature* pRootSignature,
    REFIID riid,
    void** ppvCommandSignature
    );
```

### Behavior

Creates an `ID3D12CommandSignature` from the ordered argument descriptions. The signature defines the [payload layout](#argument-records), [work type](#work-types) and state changes. The runtime copies the argument descriptions during creation; the caller's description array is not deferred GPU argument storage.

### Parameters

`[in] pDesc`

Type: **const [D3D12_COMMAND_SIGNATURE_DESC](#command-signature-desc)\***

Describes the command signature to be created with the [D3D12_COMMAND_SIGNATURE_DESC](#command-signature-desc) structure.

`[in, optional] pRootSignature`

Type: **[ID3D12RootSignature](binding.md#root-signatures)\***

Specifies the [ID3D12RootSignature](binding.md#root-signatures) that the command signature applies to.

The root signature must be specified if and only if the command signature changes one of the root arguments. Vertex-buffer or index-buffer changes alone do not require a root signature.

`riid`

Type: **REFIID**

The globally unique identifier (**GUID**) for the command signature interface ([ID3D12CommandSignature](#command-signatures)). The **REFIID**, or **GUID**, of the interface to the command signature can be obtained by using the \_\_uuidof() macro. For example, \_\_uuidof(**ID3D12CommandSignature**) will get the **GUID** of the interface to a command signature.

`[out, optional] ppvCommandSignature`

Type: **void\*\***

Specifies a pointer, that on successful completion of the method will point to the created command signature ([ID3D12CommandSignature](#command-signatures)).

### Return values

Returns an `HRESULT`: `S_OK` on successful object creation; invalid command-signature descriptions fail with `E_INVALIDARG`. Other object-allocation/device errors follow the [Direct3D 12 return-code contract](https://learn.microsoft.com/en-us/windows/win32/direct3d12/d3d12-graphics-reference-returnvalues).

When `ppvCommandSignature` is null, the method performs validation-only creation. All command-signature description checks still apply; valid input returns `S_FALSE` and no command-signature object is returned. Invalid descriptions still fail.

<a id="signature-validation"></a>

### Runtime validation

The runtime will validate the following:

- There is exactly 1 entry defining the draw/dispatch parameters
    (either `D3D12_INDIRECT_ARGUMENT_TYPE_DRAW` or
    `D3D12_INDIRECT_ARGUMENT_TYPE_DRAW_INDEXED` or
    `D3D12_INDIRECT_ARGUMENT_TYPE_DISPATCH`, `D3D12_INDIRECT_ARGUMENT_TYPE_DISPATCH_RAYS`, or `D3D12_INDIRECT_ARGUMENT_TYPE_DISPATCH_MESH`). This entry must come last.

- A `D3D12_INDIRECT_ARGUMENT_TYPE_INDEX_BUFFER_VIEW` entry can only be
    present if there is also a
    `D3D12_INDIRECT_ARGUMENT_TYPE_DRAW_INDEXED` present.

- ByteStride is 4-byte aligned

- ByteStride is large enough to hold all data

- All resource bindings are compatible with the root signature.

- Each root-view parameter slot is defined no more than once. Multiple constant entries may target non-overlapping ranges of one root-constant parameter.

- Root parameter slots do not exceed range defined by root signature

- If there are vertex buffer changes, the vb slot index is within the
    range allowed by D3D

- Entries that reference root parameter slots are sorted from smallest
    to largest root parameter index

- Root constant entries are sorted from smallest to largest
    DestOffsetIn32BitValues (including no overlap)

- If `D3D12_INDIRECT_ARGUMENT_TYPE_DISPATCH` or `D3D12_INDIRECT_ARGUMENT_TYPE_DISPATCH_RAYS` is used, then VB and IB
    bindings cannot be changed

- The root signature is specified if and only if the command signature
    indicates that 1 of the root arguments changes

- For root constants DestOffsetIn32BitValues + Num32BitValuesToSet is
    within range defined by the root signature

- No VB slot is changed more than once

- Only 1 IB change per command signature is allowed

- Num32BitValuesToSet must be greater than 0

Root-index ordering applies to entries that reference root parameters, not to the numeric enum values or VB slot numbers. A root CBV/SRV/UAV entry must target the corresponding root-descriptor type, not a descriptor table. Constant and incrementing-constant entries must target a root-constant parameter; their destination ranges must fit, be increasing and not overlap. `CONSTANT.Num32BitValuesToSet` must be positive. An incrementing constant occupies one destination value, regardless of its zero-byte payload. There may be at most one incrementing constant in the signature, and it requires tier 1.1.

Vertex-buffer slots are in the range 0–31, with no repeated slot. An index-buffer change is allowed only with `DRAW_INDEXED`, at most once. Mesh work does not acquire IA input semantics merely because its signature describes a vertex-buffer change. All root-signature visibility, deny flags and [pipeline/root compatibility](binding.md#pipeline-compatibility) still apply. `NodeMask` selects the device nodes for the object; the executing command list must be compatible with that selection.

<a id="executeindirect"></a>

## ID3D12GraphicsCommandList::ExecuteIndirect

### Declaration

```cpp
void ExecuteIndirect(
    ID3D12CommandSignature* pCommandSignature,
    UINT MaxCommandCount,
    ID3D12Resource* pArgumentBuffer,
    UINT64 ArgumentBufferOffset,
    ID3D12Resource* pCountBuffer,
    UINT64 CountBufferOffset
    );
```

### Behavior

There are 2 ways that command counts can be specified:

If pCountBuffer is not NULL, then MaxCommandCount specifies the maximum
number of operations which will be performed. The actual number of
operations to be performed are defined by the minimum of this value, and
a 32-bit unsigned integer contained in pCountBuffer (at the byte offset
specified by CountBufferOffset).

If pCountBuffer is NULL, the MaxCommandCount specifies the exact
number of operations which will be performed.

### Parameters

| Parameter | Contract |
|---|---|
| `pCommandSignature` | Required command signature that defines interpretation of every record, the final work type and affected bind point. |
| `MaxCommandCount` | A `UINT` upper bound on the number of records, or the exact record count when there is no count buffer. |
| `pArgumentBuffer` | Required buffer resource containing the signature-defined records. |
| `ArgumentBufferOffset` | Byte offset to the first record; must be four-byte aligned. |
| `pCountBuffer` | Optional buffer resource containing one 32-bit unsigned command count at `CountBufferOffset`. It may be the same resource as `pArgumentBuffer`; the selected count bytes and argument bytes have their respective bounds requirements. |
| `CountBufferOffset` | Byte offset to the four-byte count value; must be four-byte aligned. Must be zero when `pCountBuffer` is null. |

The count value is not a count of argument descriptions and is not a 64-bit query result or predicate. For example, a GPU count of `0xffffffff` with `MaxCommandCount=3` executes at most three records, never a signed negative count. Neither count form multiplies the per-record draw/dispatch dimensions implicitly.

### Return values

None. Recording errors use the [command-list error and Close contract](execution.md#close), not an `HRESULT` returned by this method.

<a id="execution-algorithm"></a>

### Execution algorithm

The semantics of this API are defined with the following pseudo-code:

Non-NULL pCountBuffer:

```cpp
// Read draw count out of count buffer
UINT CommandCount = pCountBuffer->ReadUINT32(CountBufferOffset);
CommandCount = min(CommandCount, MaxCommandCount);

// Get pointer to first command argument
BYTE* Arguments = pArgumentBuffer->GetBase() + ArgumentBufferOffset;

for(UINT CommandIndex = 0; CommandIndex < CommandCount; CommandIndex++)
{
    // Interpret the data contained in *Arguments
    // according to the command signature
    pCommandSignature->Interpret(Arguments);
    Arguments += pCommandSignature ->GetByteStride();
}
```

NULL pCountBuffer:

```cpp

// Get pointer to first command argument
BYTE* Arguments = pArgumentBuffer->GetBase() + ArgumentBufferOffset;

for(UINT CommandIndex = 0; CommandIndex < MaxCommandCount;CommandIndex++)
{
  // Interpret the data contained in *Arguments
  // according to the command signature
  pCommandSignature->Interpret(Arguments);
  Arguments += pCommandSignature ->GetByteStride();
}
```

A command count of zero executes no records. A record whose direct workload launches no primitives, groups or rays still occupies its place in the record sequence; later records and incrementing-constant indices do not collapse around it. No-work does not waive signature, resource, pipeline, alignment or recording-context validity. After the call, affected state follows the canonical [indirect reset/leakage rules](command-list-state.md#indirect), including when no records execute or generated work is predicated off; unaffected state is not cleared.

<a id="execute-validation"></a>

### Runtime validation and byte extents

The runtime validates four-byte alignment of both byte offsets, buffer resource dimensions, the argument-buffer extent implied by the maximum command count and signature stride, count-buffer extent when present, command-list type and command-signature node compatibility. A count buffer containing zero does not reduce the extent that must be valid for `MaxCommandCount`.

Let `S` be `ByteStride`, `P` the sum of the [payload byte sizes](#argument-records), `M` be `MaxCommandCount`, `A` be `ArgumentBufferOffset` and `W` the argument buffer's byte width. For nonzero `M`, the argument range must satisfy:

```text
A + (M - 1) * S + P <= W
```

The arithmetic must not overflow. The payload of the last record must fit; record-end padding after that final payload need not exist. For a present count buffer of width `C`, the selected four bytes require `CountBufferOffset + 4 <= C`, without overflow. These checks use the maximum API count, not `min(MaxCommandCount, GPUCount)`. When `MaxCommandCount` is zero, the runtime skips argument-range-size validation; alignment, buffer-type and recording-context requirements remain. A present count buffer still designates a valid four-byte count.

**History:** Earlier behavior required the final record's stride padding to fit as well. This was corrected; the final-payload extent above is the current contract.

Argument and count storage must support indirect-argument reads under the [resource/heap contracts](resources.md#heap-types). In particular, a READBACK heap's fixed COPY_DEST usage does not satisfy indirect-argument access. The public reference's phrase “any heap type” does not override this restriction. Protected argument/count buffers are prohibited.

<a id="execute-debug"></a>

### Debug-layer validation and GPU data

The debug layer checks the argument/count resources' indirect-argument access and the selected pipeline/root state. If the signature changes root arguments, the root signature set on the command list at the corresponding graphics or compute bind point must match the root signature of the command signature. This match requirement is distinct from the work pipeline's root-signature compatibility requirement. A signature with no root changes has no associated root signature, but its work command still requires its normal pipeline and root bindings.

CPU signature validation does not establish that all GPU-resident payload values are valid. Vertex/index views retain their [format, extent, alignment and fetch rules](vertex-processing.md#buffer-views). Index-buffer payloads must specify a valid [index format](vertex-processing.md#d3d12_index_buffer_view); signature creation cannot inspect GPU-resident `Format` values. Root GPU virtual addresses retain the [root-descriptor](binding.md#root-descriptors) and [constant-buffer alignment](binding.md#id3d12graphicscommandlist-setgraphicsrootconstantbufferview) contracts. A root descriptor contains an address, not a descriptor-table handle and not a size/format/stride triplet. Root SRV/UAVs retain the buffer-only, supported raw/structured interpretation of the binding owner; indirect execution does not add typed-buffer or texture root descriptors.

Non-null GPU addresses must identify valid accessible storage for the addressed operation, including its subresource/access and lifetime requirements. Null-binding cases remain those of the corresponding direct view/root-binding contract. [GetGPUVirtualAddress](resources.md#resource-gpu-address) supplies buffer addresses; adding a byte offset does not waive VB/IB/CB or root-view alignment. The indirect data buffer's four-byte alignment is separate from alignment of the GPU addresses stored in it. Shader-table addresses retain their [raytracing alignment and bounds](raytracing-pipelines.md#d3d12_dispatch_rays_desc).

<a id="recording-contexts"></a>

## Recording contexts, predication and statistics

`ExecuteIndirect` is recorded on DIRECT or COMPUTE command lists, with the restricted BUNDLE form below; it is not supported on COPY or video command lists. A COMPUTE list accepts the compute-root work types `DISPATCH` and supported `DISPATCH_RAYS`, not graphics draw or mesh work. DIRECT lists still require the pipeline appropriate to the signature's final command.

The [bundle restriction](command-list-state.md#indirect) requires a null count buffer and exactly one argument description: the work operation alone. A zero-byte incrementing-constant entry is still a second description and is not allowed in this form. Bundle admission of the wrapper does not grant every direct-work operation permission to execute in a bundle; the operation's own context rules still apply.

In an open render pass, the [complete operation table and typed-work rules](output-merger.md#render-pass-operation-surface) apply. DRAW, DRAW_INDEXED and supported DISPATCH_MESH forms retain raster/pipeline/pass access requirements. Argument/count reads must not consume writes from that pass. Indirect `DISPATCH` and `DISPATCH_RAYS` are forbidden inside an open render pass, like their direct forms. Admission of the `ExecuteIndirect` wrapper does not grant a non-raster typed-work exception.

[Predication's operation matrix](counters-queries-and-predication.md#predication-operation-matrix) classifies `ExecuteIndirect` as a wrapper: eligible generated GPU work honors the predicate; required post-call state cleanup still occurs. The 64-bit predicate value and comparison are defined by [predicate state](counters-queries-and-predication.md#predicate-state), separately from the 32-bit command count. A false predicate is not permission for invalid recording parameters.

Queries measure the generated work according to their query type, not a single aggregate “ExecuteIndirect invocation.” [Occlusion](counters-queries-and-predication.md#occlusion), [pipeline statistics](counters-queries-and-predication.md#pipeline-statistics), [mesh statistics](counters-queries-and-predication.md#mesh-statistics), [culled-primitive accounting](counters-queries-and-predication.md#culled-primitives) and [SO statistics](counters-queries-and-predication.md#stream-output-statistics) retain their precise counting rules. Runtime/driver implementation shaders do not become application draw/dispatch work for these counts.

<a id="argument-initialization"></a>

## Argument initialization and synchronization

Parameters to indirect draws/dispatches can be initialized via standard ways of writing data into buffers, such as copy commands or rendering.

Counter-based scenarios involve a variable amount of data that has been written to a buffer, via pixel shader/compute shader unordered access views with append or counter semantics. One might want to issue an indirect draw/dispatch in such a way that all of the entries in a variable length array of structures written to a buffer are fed back into the pipeline.

In D3D12, the application allocates the [32-bit UAV counter storage](counters-queries-and-predication.md#application-counters) and supplies its [counter-resource association](formats.md#buffer-uav). The application can copy the counter bytes with [CopyBufferRegion](resource-operations.md#copybufferregion), place them in a count buffer, or use shader work to produce workload arguments. The explicit counter-byte operations and their [copy/clear interactions](resource-operations.md#counter-interactions) do not implicitly copy or clear a separately associated counter.

When a copied UAV count is used as a way to recirculate variable length arrays of structures back into the pipeline, the application must be aware that there is no indication of whether the buffer holding the variable length data ran out of space. If the count is too high for the amount of space in the buffer, it means that during initialization when the buffer got full, subsequent writes were discarded, yet the counter continues going. The intent here is to efficiently enable scenarios where the application knows the worst case amount of data that could be written and allocates appropriately (or is otherwise somehow robust to having the last elements missing due to buffer full). Calling an indirect draw with a vertex count that is too high behaves predictably — attempts to read past the end of a vertex buffer have well defined [input fetch bounds semantics](vertex-processing.md#bounds).

The [UAV counter/storage rules](formats.md#buffer-uav) define the actual storage and association. The indirect command-count clamp limits the number of *records*, not a vertex/group/ray count in one record. Fetching an indirect argument record beyond its argument buffer is a different invalid range.

[Stream-output filled-size storage](geometry-shaders-and-stream-output.md#filled-size) counts bytes, not command records. It is not interchangeable with a 32-bit command count merely because both occupy four bytes. The application must produce the correctly interpreted draw or dispatch field values.

Argument and count buffers hold control data in ordinary D3D12 buffer resources; GPU-address payloads refer to separately validated data resources. No special indirect-argument resource-creation flag is required. The [buffer description](resources.md#buffer-description) and [resource flags](resources.md#resource-flags) still govern creation.

CPU writes use [Map/Unmap and CPU-access rules](resources.md#cpu-access); GPU producers use the applicable copy or shader-write contracts. Producing bytes does not itself establish that subsequent indirect reads are synchronized.

With enhanced barriers, argument and count buffers use `D3D12_BARRIER_ACCESS_INDIRECT_ARGUMENT` and the compatible `D3D12_BARRIER_SYNC_EXECUTE_INDIRECT` scope. [Barrier sync](synchronization.md#barrier-sync), [access](synchronization.md#barrier-access), [access/sync compatibility](synchronization.md#access-sync-compatibility), [buffer barriers](synchronization.md#d3d12_buffer_barrier) and [queue compatibility](synchronization.md#queue-compatibility) define producer-to-consumer dependencies. Buffers have no texture layout transition; any textures addressed by shader work retain their own [layout/access rules](synchronization.md#layout-access-compatibility).

The legacy alternative uses `D3D12_RESOURCE_STATE_INDIRECT_ARGUMENT` for argument and count reads, with applicable [transition/UAV barriers](synchronization.md#legacy-barriers) and [promotion/decay](synchronization.md#legacy-promotion-and-decay). [Cross-queue completion](execution.md#queue-waits) and object/resource lifetime remain separate requirements. The common synchronization rules, not a command-count value or CPU recording order alone, govern when produced bytes are available to indirect execution.

<a id="examples"></a>

## Worked command-signature layouts

<a id="example-indexed"></a>

### Indexed multidraw with record-end padding

In this example, the indirect argument buffer generated by the
application holds an array of 36-byte structures. Each structure only
contains the 5 parameters passed to DrawIndexedInstanced (plus padding).

The code to create the command signature description is:

```cpp
D3D12_INDIRECT_ARGUMENT_DESC Args[1] = {};
Args[0].Type = D3D12_INDIRECT_ARGUMENT_TYPE_DRAW_INDEXED;

D3D12_COMMAND_SIGNATURE_DESC ProgramDesc = {};
ProgramDesc.ByteStride = 36;
ProgramDesc.NumArgumentDescs = 1;
ProgramDesc.pArgumentDescs = Args;
```

The layout of a single structure within an indirect argument buffer is:

| | |
|---|---|
Bytes 0:3|     `IndexCountPerInstance`
Bytes 4:7|     `InstanceCount`
Bytes 8:11|    `StartIndexLocation`
Bytes 12:15|   `BaseVertexLocation`
Bytes 16:19|   `StartInstanceLocation`
Bytes 20:35|   `Padding`

<a id="example-root-vb"></a>

### Root constants and vertex buffer

In this example, each structure in an indirect argument buffer changes 2
root constants, changes 1 vertex buffer binding, and performs 1 drawing
non-indexed operation. There is no padding between structures.

The code to create the command signature description is:

```cpp
D3D12_INDIRECT_ARGUMENT_DESC Args[4] = {};
Args[0].Type = D3D12_INDIRECT_ARGUMENT_TYPE_CONSTANT;
Args[0].Constant.RootParameterIndex = 2;
Args[0].Constant.DestOffsetIn32BitValues = 0;
Args[0].Constant.Num32BitValuesToSet = 1;
Args[1].Type = D3D12_INDIRECT_ARGUMENT_TYPE_CONSTANT;
Args[1].Constant.RootParameterIndex = 6;
Args[1].Constant.DestOffsetIn32BitValues = 0;
Args[1].Constant.Num32BitValuesToSet = 1;
Args[2].Type = D3D12_INDIRECT_ARGUMENT_TYPE_VERTEX_BUFFER_VIEW;
Args[2].VertexBuffer.Slot = 3;
Args[3].Type = D3D12_INDIRECT_ARGUMENT_TYPE_DRAW;

D3D12_COMMAND_SIGNATURE_DESC ProgramDesc = {};
ProgramDesc.ByteStride = 40;
ProgramDesc.NumArgumentDescs = 4;
ProgramDesc.pArgumentDescs = Args;
```

The layout of a single structure within the indirect argument buffer is:

| | |
|---|---|
Bytes 0:3|Data for root parameter index 2
Bytes 4:7|Data for root parameter index 6
Bytes 8:15|Virtual address of VB (64-bit)
Bytes 16:19|VB size
Bytes 20:23|VB stride
Bytes 24:27|VertexCountPerInstance
Bytes 28:31|InstanceCount
Bytes 32:35|StartVertexLocation
Bytes 36:39|StartInstanceLocation

The root-constant parameters at indices 2 and 6 must each have at least one value. Creating this second signature requires that root signature; the draw-only first signature requires null `pRootSignature`.

<a id="driver-contract"></a>

## Driver and hardware responsibilities

The runtime validates and translates the public description and calls the driver's command-signature creation DDIs. The public DDI uses `D3D12DDIARG_CREATE_COMMAND_SIGNATURE_0001` with `ByteStride`, `NumArgumentDescs`, `pArgumentDescs`, `hRootSignature` and `NodeMask`. Its descriptor array uses `D3D12DDI_INDIRECT_ARGUMENT_DESC`, whose union includes the tier-1.1 incrementing-constant target. `D3D12DDI_INDIRECT_ARGUMENT_TYPE` includes draw, compute, ray and mesh work along with the state-changing arguments.

The size and creation DDI names retain their `_0001` suffix; execution uses `PFND3D12DDI_EXECUTE_INDIRECT`. These DDI suffixes are independent of command-list table revisions. For example, `D3D12DDI_COMMAND_LIST_FUNCS_3D_0033` contains `pfnExecuteIndirect` of that unversioned execution-DDI type, not a DDI renamed to `_0033`. The ray, mesh and incrementing-constant argument additions do not require newly named creation or execution DDIs.

```cpp
typedef struct D3D12DDIARG_HRESOURCE_PLACEMENT
{
    D3D12DDI_HRESOURCE hResource;
    UINT64             Offset;
} D3D12DDIARG_HRESOURCE_PLACEMENT;

typedef struct D3D12DDIARG_BUFFER_PLACEMENT
{
    union
    {
        D3D12DDIARG_HRESOURCE_PLACEMENT UMD;
    } BaseAddress;
} D3D12DDIARG_BUFFER_PLACEMENT;
```

```cpp
typedef enum D3D12DDI_INDIRECT_ARGUMENT_TYPE
{

    D3D12DDI_HCOMMANDLIST,
    D3D12DDI_HCOMMANDSIGNATURE,

    D3D12DDIARG_BUFFER_PLACEMENT CountBuffer
    );
```

**Size calculation:** Calculates the command signature size.

**Creation:** Create a command signature.

**Destruction:** Destroys a command signature.

The size DDI returns the driver's private command-signature storage size; creation returns an `HRESULT`; destruction releases the driver object. `PFND3D12DDI_EXECUTE_INDIRECT` receives the command list and signature handles, maximum count, and argument/count buffer placements. Each placement's `BaseAddress.UMD` carries the resource handle and byte offset; a null count-resource handle denotes the no-count-buffer form. The driver/hardware must interpret the selected argument format and offsets and enforce the unsigned minimum of API maximum and GPU count. The [canonical state-reset contract](command-list-state.md#indirect) assigns the post-call resetting DDI calls to the runtime.

Mesh work's [DispatchMesh DDI and stage responsibilities](amplification-and-mesh-shaders.md#mesh-driver), and ray work's [raytracing driver contract](raytracing-pipelines.md#driver-dispatch), remain distinct from signature creation and indirect interpretation. Tier-1.1's system-generated constant consumes no argument bytes; an implementation must supply its zero-based sequence and reset the affected state.

<a id="driver-lifetime"></a>

### Driver-object lifetime and execution inputs

The sizing DDI reports required driver-private object bytes as `SIZE_T`,
not the size of the GPU argument buffer and not an `HRESULT`. The runtime
supplies that private region through `D3D12DDI_HCOMMANDSIGNATURE` to the
Create DDI. The UMD initializes its state there and owns its additional
allocations, not the supplied region. A sizing call does not construct
the object.

Failed driver creation must unwind partial driver state and allocations;
the runtime does not call DestroyCommandSignature for a failed Create.
After successful driver creation, later abandonment requires destruction of
that driver object. DestroyCommandSignature releases UMD-owned state
without freeing the runtime-supplied private region. The runtime keeps an
associated root-signature object alive for this driver object's lifetime;
destroying the command signature does not transfer root-signature destruction
to the UMD.

The lifecycle's logical API association is
[CreateCommandSignature](#createcommandsignature). The creation arguments
and their `pArgumentDescs` array are borrowed for the call. The UMD must
capture the signature information it needs afterward into its own state,
rather than retain those input pointers. This array is the signature's
ordered metadata, not GPU argument records consumed by ExecuteIndirect.

`NumArgumentDescs` counts descriptions in one signature.
`ByteStride` is the byte step between complete command records, including
record padding, not the size of each individual argument. The
[record-layout contract](#argument-records) defines the consumed bytes.
`hRootSignature` is the associated driver root handle, or null when no root
arguments are changed, under the API's if-and-only-if association rule.
`NodeMask` carries the selected creation nodes after runtime processing;
it is not a GPU record count or per-dispatch dimension.

`PFND3D12DDI_EXECUTE_INDIRECT` implements the
[ExecuteIndirect API contract](#executeindirect) after resolving the API
signature and resources to driver handles. Argument/count placements are
passed by value; their `BaseAddress.UMD` members identify driver resources
and resource-relative byte offsets, not API interfaces, CPU record pointers
or bare GPU virtual addresses. The absent count buffer has a null resource
handle and zero offset.

The argument/count contents remain GPU execution inputs; recording the DDI
is not a CPU readback or proof of their validity. The API's
[byte extents](#execute-validation), [typed-work contexts](#recording-contexts),
GPU count limit, resource lifetime and access requirements remain applicable.
Signature metadata capture does not snapshot GPU argument/count bytes.
The [runtime's post-call state resets](command-list-state.md#indirect) still
apply for zero or predicated-off generated work. Reported recording failures
use the [shared callback/deferred-Close contract](execution.md#lifecycle-driver-errors);
returning from this `VOID` DDI does not report GPU completion.

Both of the following implementations are acceptable:

- Make the GPU command processor interpret the indirect argument
    buffer contents in the application-defined format

- Allocate enough storage in the current command buffer to hold
    MaxCommandCount draws. Execute a compute shader to transform from
    the application-specified format to a hardware-specific format in
    the allocated command buffer space.
